# L8180 → TX720 색 분리 LUT 이식 조사

**LUT 본체를 추출했으며, 플래시 가능한 수정 EFU는 아직 만들지 않았습니다.**
공통 표 형식은 확인했지만 채널 의미와 후단 보정까지 같다는 뜻은 아닙니다.

목표는 Windows 엡손 드라이버의 RGB 입력을 대상으로 L8180 계열 색 분리를 사용하면서,
TX720의 C/M/Y/BK를 유지하고 GY를 기존 LC에 연결하며, 고장 난 LM은 사용하지 않는 것입니다.
PB에 해당하는 출력분은 살아 있는 BK에 합쳐야 합니다.
LC 카트리지에 실제 회색 잉크를 공급하는 준비는 별도이며 LUT가 잉크 색을 바꾸지는 않습니다.

## 입력 및 추출

- 제공된 `FWCJ21TL.efu` SHA-256:
  `2973accac530f01e9fe09ace5ef8c0034ae4f27dc5e12becf26abab050492a04`
- RCX 버전 `05.55.OP09QA.FY20`, 대상 `*.*.OP*.FY20`.
  패키지에는 `EPSONSIGN`과 `EPSON IPLJ` 이미지 세 개가 있습니다.
- 압축 해제된 데이터에서 `L8180 Series`, `ET-8550 Series`, `EW-M973A3T Series` 표기를 확인했습니다.
  업데이트 EXE를 실행하거나 이 EFU를 TX720에 기록하지 않았습니다.
- SquashFS 두 개는 네트워크 구성요소였고, 실제 색 처리 데이터는 별도 CROM 내부에서 찾았습니다.

CROM 초기화 복사 표를 따라 다음 부트스트랩 코드를 재구성했습니다.
원본 IPL 1의 페이로드 기준 `0x57004..0x9bbfc`는 `0x43718000`으로,
`0x9bbfc..0x9c900`은 `0x43768000`으로 복사됩니다.
`0x43768334`는 압축 스트림의 위치·크기·토큰 수를 읽습니다.
Huffman 처리에는 하드웨어 레지스터 `0xf0051000`이 관여합니다.

오프라인 추출기는 DHT의 canonical Huffman 표 세 개와 3바이트 LZ 토큰을 해석합니다.
리터럴 시작은 스캔 헤더 끝 + Huffman 크기 + **8바이트**입니다.
헤더의 패딩 토큰 수를 이 8바이트 간격과 혼동하면 잘못 추출됩니다.
LZ에서 거리 0/길이 255인 토큰은 리터럴 256바이트가 아니라 건너뛰기 표식입니다.

컨테이너 다섯 개에 연속 스트림이 있어 총 **8개 구간**을 추출했습니다.
각 구간의 리터럴 소비량은 선언된 크기와 일치합니다.
첫 8,945,996바이트 구간은 원본 ARM LZ 복사 루프와 복사 함수를 Unicorn에서 실행한 결과와
소프트웨어 추출 결과가 전체 바이트 단위로 일치합니다.
Huffman 토큰은 소프트웨어에서 미리 해석했고 토큰 준비 대기는 stub 처리했습니다.
하드웨어 Huffman 엔진이나 실제 프린터를 실행한 검증은 아닙니다.

런타임 배치도 연결됩니다:

- 첫 주 구간 `0x43871000 + 8945996 = 0x440f914c`
- 두 번째 주 구간 `0x440f914c + 20524452 = 0x4548bef0`

[구간별 해시](../reports/l8180-crom-extraction.json),
[원본 ARM LZ 비교 검증](../reports/l8180-native-lz-validation.json).

## 실제 색 처리 리소스

TX720의 `0x41b31dac`은 `CMM-ID`, `INK-ID`, `ink_set`, `ubec_dither`,
`ubec_extbl`, `media`, `H-RES`, `V-RES`, `DocType` 등의 설정 열을 찾습니다.
L8180에도 대응하는 이름을 사용하는 처리와 설정 데이터가 있습니다.
TX720 원본의 `ESCPR2` / `EpsonRGB` 표기뿐 아니라, 추출된 설정에서 `E-RGB` 모드에 대한
개별 CMM 프로필도 확인했습니다. 현재 Windows 출력물의 실제 전송 모드를 캡처한 것은 아닙니다.

리소스 헤더의 공통 7바이트는 `7acf865c7d903c`이며 다음 바이트는 `b9` 또는 `ba`입니다.
원본 TX720의 `0x41b2daf4`를 실행해 리소스를 풀고,
`ba` 형식은 `0x41b2d44c` 후처리를 적용했습니다.
힙/핸들 할당·잠금·반환 경계는 에뮬레이터의 별도 버퍼로 모델링했습니다.
원본 장치의 RTOS나 Windows 실행 파일은 실행하지 않았습니다.

| 항목 | TX720 | L8180 |
|---|---:|---:|
| 압축 리소스 | 60 | 179 |
| CLUT 포함 EP355 프로필 | 28 | 118 |
| 입력 채널 | 3 | 3 |
| 출력 채널 | 6 | 6 |
| 각 입력 축 격자 수 | 17 | 17 |
| CLUT 격자 데이터 바이트 | 29,478 | 29,478 |
| 확인한 inkset 코드 | 3 | 54 |
| CLUT 채널 식별자 순서 | `1,4,2,5,3,0` | `1,2,3,12,7,13` |

EP355에는 `rstp`, `inkd`, `cdbg`, `mdbg`, `gama`, `encd`, `clut` 등의 태그가 있고,
TX720 프로필 일부에는 `egry`, `mlut`도 있습니다.
CLUT의 형식·격자가 같아도 `inkd`와 후단 잉크/계조 처리를 건너뛸 수는 없습니다.
L8180 추출 리소스가 구형 TX720 코덱/후처리에서 정상 반환됐다는 사실은
최신 기기의 모든 처리 의미까지 동일하다는 보증이 아닙니다.

[TX720 프로필 구조](../reports/tx720-color-profile-inventory.json),
[L8180 프로필 구조](../reports/l8180-color-profile-inventory.json).

## 아직 이식본을 만들지 않은 이유

- 추가 채널 `12/7/13`의 정확한 의미와 TX720의 물리 채널 연결을 검증해야 합니다.
  채널 개수가 같다는 이유로 순서만 바꿔서는 안 됩니다.
- 프로필 ID는 전 기종 공통 용지 식별자가 아닙니다.
  예를 들어 **ID 441은 TX720에서는 `S_RC`, L8180에서는 `VELVET_FA`**입니다.
  Windows용 `E-RGB` 설정을 용지·품질과 함께 대조해야 합니다.
- PB/BK를 합치는 위치, 포화 처리, GY 출력, LM=0을 후단 보정까지 확인해야 합니다.
  별도 회색 처리 태그가 LM을 다시 생성하는지도 확인 대상입니다.
- LUT를 이식하더라도 실제 잉크·헤드·드롭량·용지에 대한 색 정확도는 별도 검증이 필요합니다.

기존 v1~v4 EFU에는 이 LUT 이식이 포함되어 있지 않습니다.

## 재현

```bash
python3 tools/extract_l8180_crom.py FWCJ21TL.efu /tmp/l8180-crom
```

제공된 원본 해시만 받으며, 기존 출력 디렉터리는 덮어쓰지 않습니다.
EFU의 ZIP CRC와 컨테이너 표식을 확인한 뒤 오프라인으로 추출합니다.

원본 TX720 분석 파일과 L8180 추출 파일을 갖춘 분석 루트에서는 다음을 실행할 수 있습니다.

```bash
python3 tools/extract_color_resources.py \
  --analysis-root /path/to/firmware-analysis --output /tmp/color-resources
```

분석 루트에는 원본 미국판 `us/part1.ipl`, `us/part2.ipl`,
`us/crom-extracted/{40000000,41a0d000,43e51000}.bin`,
그리고 `l8180/crom-extracted/000b4000-0.bin`이 필요합니다.
Unicorn은 Python 환경 또는 분석 루트의 `python-libs`에 설치합니다.
원본·추출된 전체 펌웨어 데이터는 저장소에 추가하지 않았습니다.
