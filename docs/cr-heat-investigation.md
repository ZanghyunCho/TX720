# CR 모터 발열 감속 — 분석 중

**CR 보호의 인쇄 전 추가 대기만 우회하는 [미국판 v4 실험 후보](us-cr-wait-v4.md)를 만들었습니다.**
실제 속도 개선·온도 안전성은 미검증이며, 모든 보호 기능을 해제한 파일이 아닙니다.
아래 선행 조사에서 “없음/미확인”은 해당 조사 단계의 기록입니다. v1~v3에는 이 변경이 없습니다.
현재 조사 대상은 제공받은 미국판 `21.21.AW03G6.FY10`입니다.

## 사용자 기기의 관찰

- 연속 문서 출력 약 10~20장 뒤 감속하며 품질 설정에 따라 시점이 다릅니다.
- 약 20분 아무 작업 없이 기다려야 속도가 회복됩니다.
- 전원을 켠 채 기다려야 회복된다고 보고했습니다.
- 서비스 프로그램에 CR Motor Heat Protection 관련 항목이 있으나 Check/Initialize/Reset 형태이고,
  지그 등 장비가 필요해 현재 사용할 수 없다고 보고했습니다.

이는 모터 구동량을 누적하고 동작 시간에 따라 냉각값을 계산하는 방식과 부합하지만,
발열 제한의 실제 코드·변수·단위는 아직 확인하지 못했습니다.
모터에 직접 온도 센서가 없더라도 발열 추정은 가능하며,
지역별 기후 설정 때문에 감속한다는 근거는 아직 없습니다.

## 확인한 범위

- 원본 ROM/CROM의 ASCII 문자열에서 Heat/Thermal/Motor 명칭만으로 제어 루틴을 찾지 못했습니다.
  공장 점검용 `CR Move Check` 문자열은 있으나 발열 제어라는 근거는 아닙니다.
- 20분과 같은 숫자라는 이유로 상수 `1,200,000`을 후보로 추적했습니다.
  해당 위치 `0x41a4062c`는 `0x41a40308`의 표 작성에서 다른 수치들과 함께 사용되며,
  `0x41a40280`은 약 1/1000 스케일 변환입니다. 시간·발열 제한이라는 근거가 없어 패치하지 않았습니다.
- 공개 도구의 PX720WD/TX720WD 모델 항목과 devices.xml의 TX720 항목을 읽었습니다.
  모델별 EEPROM 접근 및 통계·폐잉크 정보는 있으나 해당 항목만으로 CR 발열 제어 주소를 식별하지 못했습니다.
  외부 도구 실행이나 장치 통신, EEPROM 쓰기는 하지 않았습니다.

공개 참고 자료:
[epson_print_conf 모델 정의](https://github.com/Ircama/epson_print_conf/blob/main/epson_print_conf.py),
[ez-reset devices.xml](https://github.com/CiRIP/ez-reset/blob/master/src/ez_reset/devices.xml).
이는 해당 프린터의 온도·전류 또는 부하를 측정한 자료가 아닙니다.

## 다음 확인에 필요한 자료

사용 중인 서비스 프로그램의 실행 파일을 정적으로 분석하면,
해당 CR 항목이 사용하는 명령·EEPROM 주소·응답 형식을 펌웨어와 대조할 수 있습니다.
Initialize/Reset이 무엇을 바꾸는지 확인하기 전에는 이를 비활성화 기능이라고 가정할 수 없습니다.
지그 없이 초기화하거나 의미를 확인하지 않은 값을 EEPROM에 쓰는 수정은 아직 하지 않았습니다.


## 업로드된 서비스 프로그램 정적 분석 (2026-11-14)

분석 입력 `AdjProg.exe` SHA-256:
`b78979648e6864d22acd76fbea2f76578cdc68ecfd0fce66bc6b60624127721f`.
Windows 실행 파일과 DLL은 실행하지 않았습니다. ZIP의 사용 설명은 작업 지시로 사용하지 않았습니다.
아래 주소는 PE 이미지 베이스 `0x400000` 기준 가상 주소입니다.

- `0x679814`: CR motor drive dispersion 측정 시퀀스를 실행한다는 확인 문구.
- `0x67987c`: 측정 편차 값을 자동 등록한다는 확인 문구.
- `0x6795b9`: 교체 부품 선택이 틀리면 EEPROM에 올바른 열 보호 값이 등록되지 않고,
  연속 인쇄 중 CR 모터가 비정상적으로 발열할 수 있다는 프로그램 자체 경고.
- `0x5285ce` 부근의 화면 처리에서 측정 함수 `0x526f63` 또는 등록 함수 `0x526436`으로 분기합니다.
- 등록 함수 `0x526a9a`에서 논리 항목 `0x1b..0x1e`를 준비하고,
  `0x4daf2a`로 값을 구한 뒤 `0x4c48ee`로 등록합니다.
- `0x4c48ee`는 `0x4db16e`로 논리 항목을 주소 목록으로 변환하고,
  `0x4c4649`를 통해 값의 바이트를 순차 전달합니다.
  파일에 들어 있는 초기 테이블에서는 논리 항목 `0x1b`가 주소 인덱스 `0x97`에 연결됩니다.
  **모델 선택 후 테이블 변경 여부, 값의 의미 및 유효 범위는 아직 확인하지 않았습니다.**
  따라서 `0x97`을 확정된 비활성화 주소나 사용자에게 쓰기를 권장할 값으로 취급할 수 없습니다.
- 등록 뒤 `0x506819` 호출은 `1b 7c 00 07 00 [두 컨텍스트 바이트] 0a f5 05 [값] 00`
  형태의 서비스 명령을 구성합니다. 보정 반영인지 다른 동작인지는 펌웨어 대조가 필요합니다.

이 결과는 해당 메뉴가 모터/기구 교체 후의 보정 절차라는 근거입니다.
열 보호 ON/OFF 옵션이나 감속 임계값을 찾았다는 의미는 아닙니다.
이번 분석으로 만든 열 보호 해제 펌웨어는 없으며, EEPROM 쓰기나 장치 통신도 하지 않았습니다.


### 추가 추적: 측정 및 펌웨어 전달 경로

- 서비스 측정은 `0x526f63 → 0x526ca9 → 0x526ea8 → 0x526ef2`를 거쳐
  `0x40ce1c(10, 0x678db0, 0)`의 명령 시퀀스 해석기를 호출합니다.
  `0x678db0`은 단일 장치 명령이 아니라 10개 그룹의 호스트 측 작업 표입니다.
- `0x52613c`와 `0x52625e`는 공통 함수 `0x52615b`로 측정값을 읽습니다.
  서비스 명령 생성 함수 `0x506a5f`에 각각 인덱스 3, 2를 전달해 상위/하위 바이트를 합칩니다.
  이 명령은 `1b 7c 00 07 00 [두 컨텍스트 바이트] 74 8b 3a [인덱스 LE16]`입니다.
  측정값 허용 범위는 첫 경로 `0x202..0x2fb`, 두 번째 `0x5e3..0x7e1`입니다.
  물리 단위는 확인되지 않았습니다.
- 각 경로는 세 번의 측정값을 사용합니다. `0x526298`은 모든 쌍의 차이가 ±15 이내인지
  확인하고 합계를 계산합니다. `0x526358`은 두 번째 합계로 보정값을 계산해
  `0x506819`의 서비스 명령에 전달합니다. 이 역시 ON/OFF 전환이라는 근거가 아닙니다.
- 대화상자 리소스 128과 1678의 `CR heat protection offset`은 편집 입력칸이 아니라
  그룹 상자(`BUTTON / BS_GROUPBOX`, ID `0x5b0`) 제목입니다.
  리소스 1678에는 별도 입력칸 `Fuka_kc` / `Fuka_kd`도 있습니다.
  적용 모델과 계수의 의미는 미확정입니다. 단순한 제목을 해제 옵션으로 오인하면 안 됩니다.
- 미국판 CROM `0x41a5c4e8`은 주소가 `0x1fc`보다 작은지 검사한 뒤
  EEPROM 캐시 `0x4014deba + 주소`에서 한 바이트를 읽는 함수입니다.
  `0x41a4d258`은 `0x4d, 0x9a, 0x98, 0x4c, 0x99, 0x97`을 읽습니다.
  이어 `0x41a4d33c`는 이 값을 내부 메시지 오프셋 `0x0a..0x0f`에 복사합니다.
  해당 메시지는 `[+6]=0x0a`, `[+7]=0`, `[+8]=호출 인자`이며,
  `0x41acd300 → 0x41acd454`를 통해 채널 2의 MMIO 전송 경로로 전달됩니다.
  따라서 서비스 프로그램의 `0x97` 주소 후보에 대응하는 실제 펌웨어 읽기 경로를 찾았습니다.
  그러나 수신 측에서 이 바이트가 발열 계산·감속 판단에 미치는 영향은 아직 미확인입니다.

위 주소들은 원본 미국판에서 읽은 코드입니다. 실제 장치에서 측정 시퀀스를 실행하거나
보정값을 변경하지 않았으며, 열 보호를 해제한 결과를 뜻하지 않습니다.


## Xtensa 수신부 및 추가 대기 경로 식별

`40000000.bin`에서 Xtensa 실행 코드와 상수 데이터를 식별했습니다.
벡터 `0x40000000`은 `s32e` 네 번과 `rfwo`, `0x40000040`은 `l32e` 네 번과 `rfwu`로 해석됩니다.
ARM 디스어셈블만으로 이 영역을 분석할 수 없었던 점을 수정했습니다.

- 송신/수신 MMIO 테이블에서 채널 2는 `0x400b6430 / 0x400b6460`입니다.
- 초기화 복사 표 `0x400b64a0`은 소스 `0x400b64c4`의 `0x5080`바이트를
  런타임 `0x80010000..0x80015080`으로 연결합니다. 앞 `0x794`바이트는 상수 풀입니다.
  시작 코드가 설정하는 Extended L32R 상수 풀을 반영해야 관련 함수와 포인터가 올바르게 해석됩니다.
- 수신 함수 `0x400b189c`, 하위 명령 0은 메시지 `+9..+15` 일곱 바이트를 받아
  `0x400ace74 → 0x400aa66c / 0x400ae4a4`로 넘깁니다.
  CR 경로 `0x400aa66c`에서 마지막 바이트(EEPROM `0x97`)는 부호 있는 보정 계수로 사용됩니다.
- CR 대기 조회 `0x400aaa78`과 PF 조회 `0x400aea08`은 공통 함수 `0x400acc84`에
  서로 다른 계수 표와 상태 주소를 넘깁니다. 공통 함수는 상태 수준에 대한 구간별 계산으로
  대기값을 구합니다. CR 표 `0x4009f688`의 경계값은 `229989 / 240941 / 247512`입니다.
  이 숫자의 물리 단위나 실제 모터 온도를 단정하지 않습니다.
- 수신 하위 명령 4는 `0x400acf00`에서 CR/PF 조회값의 최댓값을 반환합니다.
  ARM `0x41a4d59c → 0x41a4d31c → 0x41a34428`이 이 값을 받고,
  0보다 크면 `0x41a38ef0 → 0x41acc024`의 대기 경로를 실행한 후 인쇄 동작을 이어갑니다.

v4는 CR 조회 진입부 네 바이트만 `movi.n a2,0; ret.n`으로 바꿉니다.
PF 조회·표·기존 모터 구동 코드·보정 EEPROM은 수정하지 않습니다.
180개 Xtensa p-code 실행 사례에서 원래 CR/PF 수치 계산과 수정 후 CR=0/PF 유지 및 ABI를 확인했습니다.
원본 ARM 압축 해제기 실행으로 v3 대비 정확히 네 바이트만 바뀌는 것도 확인했습니다.

소프트웨어 검증과 실제 발열 안전성은 별개입니다. 센서리스 모델도 실제 과열을 막는 기능이며,
이 우회로 연속 출력 중 모터나 구동 회로가 손상될 가능성이 있습니다.
