# 미국판 무칩·잔량 100% 후보 v1

[후속 후보 v2](us-chipless-candidate-v2.md)는 별도 상태 전달 경로와 잔량 getter 수정을 추가합니다. 실기 성공은 아직 미검증입니다.

**실기 실패 보고:** 사용자가 v1 업데이트 성공 및 전원 재시작 후에도 본체에
카트리지 장착 요구가 나타난다고 보고했습니다. v1은 해당 기기의 무칩 사용을
해결하지 못했습니다. 아래 함수 검증 결과를 실제 동작 성공으로 해석하지 마세요.

## 실패 후 추가 조사

- v1 패키지에서 읽은 코드로 원본 초기화 함수 `0x41a36ec8`도 실행했습니다.
  속성·큐 서비스를 모의 구현하고 버스 설정·전원/클록·임계 구역 서비스를 격리한 조건에서는
  반환 0, 채널 상태 6개 모두 0, 활성 마스크 `0x3f`를 얻었습니다.
  실제 장착 요구 오류는 아직 재현하지 못했으며 이 테스트도 실기 성공 근거가 아닙니다.
- 문자열 테이블에는 `Install the ink\ncartridges.\nSee the setup sheet\nfor details.`와
  `Install ink cartridges\nthat came with product.\nClose the scanner unit.\nInitialization starts.`가
  별도로 존재합니다. 전자는 언어 테이블 인덱스 302, 후자는 194입니다.
  사용자가 본 문구가 어느 것인지는 아직 확인하지 못했습니다.
- v1의 더미 잔량 메시지는 채널 상태 `0x80`이며 일반 잉크 상태 `0x83`과 다릅니다.
  원본 변환 함수에서 두 값은 속성 `0x42D`에 각각 0과 1을 만듭니다.
  이것이 실기 실패의 원인인지는 확인하지 않았습니다.
- 따라서 추가 읽기 경로나 화면의 조건을 확인하지 않고 오류 함수의 반환값만
  강제하는 후속 펌웨어는 아직 배포하지 않습니다.

**실기 검증 전 실험본입니다. 부팅·무칩 인쇄·실제 화면 표시·복구 성공은 확인하지 않았습니다.**
ARM 함수 실행 검증은 통과했지만, 완성·검증된 무칩 펌웨어라는 뜻은 아닙니다.

[후보 파일 다운로드](https://raw.githubusercontent.com/ZanghyunCho/TX720/main/firmware/FWC365TL_US_chipless_candidate_v1_EXPERIMENTAL.efu)

대상 원본은 제공받은 미국판 `FWC365TL.efu`, 버전 `21.21.AW03G6.FY10`, 대상 `AW*FY10`입니다.
기존의 스캐너 유닛 닫힘 패치를 포함하며 언어 리소스·대상 식별자·두 번째 IPL은 유지합니다.
다른 버전이나 일본판에 이 오프셋을 적용하면 안 됩니다.

## 변경과 근거

원본 ROM의 `0x48974`는 칩 데이터를 비트 단위로 읽어 40바이트 RAM 캐시에 넣습니다.
상위 코드가 이 캐시를 검사해 카트리지 승인·잔량 상태를 결정합니다.
이 읽기 함수를 76바이트 ARM 코드로 대체해 물리 칩 대신 합성 레코드를 반환합니다.
원래 함수 영역 안에서 끝나며 압축 RAM 코드·부트 후 코드 쓰기·추가 실행 영역은 필요 없습니다.

합성 레코드는 40바이트를 0으로 초기화한 뒤 필드 7, 8, 9를 각각 1, 5, 4로 만듭니다.
필드 13·14는 각각 3, 필드 33은 `0x6e`입니다. 이것은 실제 상용 카트리지 덤프가 아닙니다.
요청한 비트 수와 무관하게 해당 캐시 40바이트를 모두 갱신하는 의도적인 동작 변경입니다.

원본 함수 `0x41a35de0`가 이 데이터를 더미 카트리지로 인식합니다.
원본 승인 경로 `0x41a377b4`는 이 경우 인증·잔량 재기록 경로를 건너뛰고 성공을 반환합니다.
원본 `0x41a35e4c`가 여섯 채널 모두를 인식하면 잔량 작성 함수 `0x41a40c84`는
채널마다 상태 `0x80`, 잔량 100을 기록합니다. 메시지 작성 함수가 이를 큐 메시지 `0x32`로 보냅니다.
독립 오류 집계 함수를 무조건 성공으로 바꾸거나 기존 오류 문구를 삭제하지 않습니다.

물리 칩 읽기 대신 데이터를 공급하는 방식이므로 칩 없는 동작을 목표로 합니다.
전체 부팅·인쇄 상태 머신은 실행하지 않았으며 다른 차단 조건이 남을 수 있습니다.
실제 잉크 공급은 별도로 필요하고, 100% 표시는 실제 잉크 양을 측정하지 않습니다.

## 확인한 범위

패키지에서 다시 읽은 수정 ARM 코드를 Unicorn 2.1.4로 실행했습니다.

- 6채널 × 기존 캐시 값 256종 × 읽기 요청 2종 = 3,072회.
- 원본 읽기 디스패처를 6채널 선택 마스크 64종으로 실행해 선택한 채널만 갱신됨을 확인했습니다.
- 합성 레코드, 반환값, 스택·보존 레지스터, 40바이트 양쪽 경계를 검사했습니다.
- 원본 승인 함수를 기존 상태 256종 × 6채널 = 1,536회 실행했습니다.
  모두 성공하고 채널 상태 6개가 0으로 갱신됐습니다.
- 레코드의 핵심 필드를 깨뜨린 음성 대조군 18개에서는 원본 더미 판정이 실패했습니다.
- 원본 잔량·메시지 작성 경로를 모드 값 0~255로 실행했고, 모두 6색 100%와 상태 `0x80`을 만들었습니다.
- ZIP CRC, IPL 합계·salted SHA-1, 변경 바이트 범위, 지역 메타데이터, 두 번째 IPL 보존을 검사했습니다.

RTOS 속성 서비스는 메모리 사전으로 대체하며 미지정 속성은 0으로 반환합니다.
원본 읽기 디스패처의 스케줄러 진입·버스 유휴 상태 복원도 테스트 stub으로 대체합니다.
이벤트 송신은 인자 기록으로, 메시지 할당·송신은 고정 테스트 버퍼로 대체합니다.
이 조건에서의 함수 결과이며 실제 프린터 통신·화면·인쇄 검증은 아닙니다.

정확한 [패치 기록](../reports/us-chipless-candidate-v1-patch.json)과
[실행 결과](../reports/us-chipless-candidate-v1-validation.json)를 함께 제공합니다.

## 원본에서 재현

```sh
python3 tools/patch_us_chipless_candidate.py FWC365TL.efu output/US_chipless_candidate_v1.efu --manifest output/patch.json
python3 tools/validate_us_chipless_candidate.py --analysis-root /path/to/firmware-analysis output/US_chipless_candidate_v1.efu --output output/validation.json
python3 tools/verify_packages.py
```

정확한 원본 SHA-256만 허용하고 기존 출력 파일은 덮어쓰지 않습니다.
실행 검증에는 원본에서 추출한 미국판 CROM 데이터가 필요하며 원본·추출 데이터는 저장소에 포함하지 않습니다.
